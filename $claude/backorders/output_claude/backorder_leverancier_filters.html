Backorder-leverancier filters rechtstreeks in de database

BAB · Odoo 18.0 · gedeelde ir.filters op stock.move · genoteerd 2026-06-25

Doel

Drie gedeelde favorieten aanmaken op het scherm Voorraad → Rapportage → Moves Analysis (stock.move), die de producten tonen die nog in backorder staan bij de leverancier — d.w.z. het restant van een gedeeltelijk ontvangen inkomende levering dat nog moet binnenkomen.

De filters spiegelen je bestaande verkoop-trio (Besteld / Besteld per contact / Besteld per product), maar met bron = leverancierslocatie i.p.v. interne voorraad, en met de extra voorwaarde backorder_id is set.

Wat we aanmaken

FavorietGroep opToont
Backorder leverancier—alle backorder-moves (regelniveau)
Backorder leverancier per contactpartner_idper leverancier
Backorder leverancier per productproduct_idper product — de lijst die we willen

Het domein achter alle drie (identiek; enkel de groepering verschilt):

["&", "&",
  ("location_id", "in", [<LEVERANCIER_LOC>]),
  ("state", "in", ["waiting", "confirmed", "partially_available", "assigned"]),
  ("picking_id.backorder_id", "!=", False)]

Hoe Odoo favorieten opslaat

Een opgeslagen zoekopdracht is één rij in de tabel ir_filters. De relevante kolommen:

KolomWaardeBetekenis
namebv. "Backorder leverancier per product"label in het Favorieten-menu (NOT NULL)
model_idstock.movetechnische modelnaam, niet de id (NOT NULL)
domainzie hierbovenfilter, als tekst (NOT NULL)
context{'group_by': ['product_id']}o.a. de groepering (NOT NULL)
sort[]sorteervolgorde (NOT NULL — leeg = standaard)
user_idNULLNULL = gedeeld met alle gebruikers
action_idid van Moves Analysisonder welke actie/scherm de favoriet verschijnt
is_defaultfalseniet als standaard opdringen

Waarom niet gewoon de ID's 4 en 492 hardcoden? Die kwamen uit de lokale DB. Op productie kunnen de leverancierslocatie en de actie een ander id hebben. De SQL hieronder zoekt beide daarom op via hun xmlid in ir_model_data, zodat ze overal kloppen.

Stappenplan

De SQL portable — geen harde ID's

Eén transactie die de drie filters in één keer aanmaakt. De leverancierslocatie en de Moves-Analysis-actie worden via hun xmlid opgezocht en in het domein ingevuld. De NOT EXISTS voorkomt duplicaten als je het per ongeluk twee keer draait.

BEGIN;

WITH ref AS (
  SELECT
    (SELECT res_id FROM ir_model_data
       WHERE module='stock' AND name='stock_location_suppliers') AS loc,
    (SELECT res_id FROM ir_model_data
       WHERE module='stock' AND name='stock_move_action')        AS act
)
INSERT INTO ir_filters
  (name, sort, model_id, domain, context,
   user_id, action_id, is_default, active, create_date, write_date)
SELECT
  v.name,
  '[]',
  'stock.move',
  '["&", "&", ("location_id", "in", [' || ref.loc ||
    ']), ("state", "in", ["waiting", "confirmed", "partially_available", "assigned"]),'
    || ' ("picking_id.backorder_id", "!=", False)]',
  v.context,
  NULL,            -- gedeeld
  ref.act,         -- onder Moves Analysis
  false, true, now(), now()
FROM ref,
     (VALUES
        ('Backorder leverancier',             '{}'),
        ('Backorder leverancier per contact', '{''group_by'': [''partner_id'']}'),
        ('Backorder leverancier per product', '{''group_by'': [''product_id'']}')
     ) AS v(name, context)
WHERE NOT EXISTS (
  SELECT 1 FROM ir_filters f
  WHERE f.name = v.name AND f.model_id = 'stock.move'
);

COMMIT;

Wil je ze op exact dezelfde plek als je verkoop-favorieten? Kijk eerst welke actie die gebruiken en neem dat id over i.p.v. stock_move_action:

SELECT DISTINCT action_id, count(*)
FROM ir_filters
WHERE model_id='stock.move' AND user_id IS NULL
GROUP BY action_id;

Staat daar één action_id (bv. dat van "Besteld"), vervang dan in de SQL ref.act door dat getal.

Verifiëren

Vooraf — resolven de xmlids? (verwacht: twee rijen met een res_id)

SELECT module, name, res_id FROM ir_model_data
WHERE module='stock' AND name IN ('stock_location_suppliers','stock_move_action');

Achteraf — staan de drie filters er met een correct ingevuld domein?

SELECT id, name, context, domain
FROM ir_filters
WHERE model_id='stock.move' AND name LIKE 'Backorder leverancier%'
ORDER BY id;

In het domein moet [<getal>] staan (de echte leverancier-locatie-id van productie), niet het woord loc.

Inhoudelijke check — hoeveel producten staan er nu in backorder? (vervang 4 door de prod-locatie-id uit de vorige query)

SELECT count(*) AS moves, count(DISTINCT product_id) AS producten
FROM stock_move m JOIN stock_picking p ON p.id = m.picking_id
WHERE m.location_id = 4
  AND m.state IN ('waiting','confirmed','partially_available','assigned')
  AND p.backorder_id IS NOT NULL;

Ter referentie: in de lokale test-DB gaf dit 214 moves over 170 producten.

Zichtbaar maken

Geen serverherstart nodig. ir.filters worden live gelezen telkens een actie geopend wordt. Eén browserverversing volstaat: de drie favorieten verschijnen onder Moves Analysis → Favorieten, voor alle gebruikers (want user_id = NULL).

Terugdraaien

Eén regel verwijdert ze weer (gericht op naam + model, raakt niets anders):

DELETE FROM ir_filters
WHERE model_id='stock.move' AND name LIKE 'Backorder leverancier%';

Aandachtspunten

  • Echte backorders vs. alles wat nog komt. Deze filters tonen enkel het restant ná een gedeeltelijke ontvangst (backorder_id is set). Wil je óók de volledig nog-niet-ontvangen inkomende leveringen, laat dan de laatste voorwaarde ("picking_id.backorder_id", "!=", False) weg.
  • Bron = leverancierslocatie. location_id = Vendors vangt inkomende moves (ook dropship). Klopt voor "besteld bij de leverancier".
  • Groep "per contact". partner_id op de move is de leverancier van de ontvangst — net zoals bij je verkoop-favoriet, maar dan aan de inkoopkant.
  • Rechtstreekse INSERT omzeilt de ORM. Voor ir.filters is dat veilig (pure data). create_uid/write_uid blijven leeg — dat mag. Geen orm_signaling of cache-bust nodig.
